# 背压、稳定性与安全边界

## 范围

本轮按数据从生产端到消费端的方向审查项目自有 WinUI、服务与原生适配代码，以及实际接入的 UxPlay 网络、配对和渲染路径；同时检查启动、依赖加载、构建和打包的信任边界。静态素材、本地化和安装模板没有持续生产队列。第三方编解码器、密码库及显示驱动内部不属于逐行审查范围，不能据此宣称整个进程不存在漏洞或具备绝对内存上限。

构建仍使用固定的官方来源、源码哈希、受控补丁和依赖清单，不放宽 TLS、DLL 搜索路径或配对验证。背压与初次安全修正的运行记录放在忽略的 `.runtime/qa-backpressure/`，会话授权、目标地址及网卡边界复测放在 `.runtime/qa-network-boundaries/`，不包含真实设备密钥或媒体内容。

## 生产与消费策略

| 链路 | 容量与满载策略 | 停止、换源及失败 |
| --- | --- | --- |
| 镜像编码视频 → appsrc | 队列最多 68 MiB、120 个缓冲；已排队时间达到 2 秒时暂停继续输入。字节预算兼容已有 64 MiB 合法访问单元及参数集。应用 push 串行，不使用会破坏帧依赖的 leaky 策略 | 等待最多 5 秒，持续检查停止、重置、失败、EOS 和源状态；永久过载只报告一次资源错误，进入既有接收失败/重试路径 |
| 编码音频 → appsrc | 最多 4 MiB、256 个缓冲，同样以 2 秒排队时间作为补充阈值 | 同上；EOS 设置取消标志，无须等待准入锁 |
| GStreamer → 消息消费者 | 音频保留 ERROR/EOS；直接视频另保留 ASYNC_DONE；镜像另保留视频 sink 的 STATE_CHANGED。每类最多一个待处理消息；直接视频每轮处理最多 32 条 | 出队及源重建时维护类别状态；窗口句柄和 D3D 上下文仍在同步处理器中处理 |
| 原生事件 → WinUI | 固定 64 项，合并相邻完全重复事件；普通事件先被淘汰，保留 Fatal 和最新解码切换结果 | 接收器停止时清空，不改变既有事件 ABI |
| 桌面控制 → 原生/网络 | 托管层一个活动命令，无等待队列；超量调用返回现有 ERROR_BUSY。原生音频控制和定位也共用一个准入 | 停止禁止新命令并撤销尚未开始的工作；每次网络写入前复核原媒体所有者和内容代次，旧结果不能应用到新来源 |
| 媒体快照及活动 | 8 KiB JSON、严格有界解析、固定节奏事件历史；UI 元数据和活动轮询串行 | 换源清空旧状态；保留现有 150/50 毫秒轮询分工 |
| 音乐封面 | 单个读取、解码、背景准备链；仅保存一个最新待处理描述。编码内容不超过 2 MiB | 换源或关闭撤销待处理内容；活动工作返回后复核代次，不恢复旧封面 |
| 背景纹理 | 一个解码、CPU 准备、上传和渐变任务，加一个最新请求；图片尺寸、像素、纹理帧数和 Composition 图层已有固定边界 | 清空立即生效；每个不可取消 WinRT 阶段结束后复核取消，失败释放工作泵 |
| SVG 尺寸/DPI 变化 | 全控件最多 4 个解码任务，一个活动代次加一个最新尺寸；固定 200 帧缓存 | 初次仍渐进显示，完整缓存重建后替换；按经过时间取当前帧，不重播积压帧 |
| 视频背景与信息浮层 | 背景一个完整采样/处理任务；信息浮层一个栅格任务加最新文本/尺寸/DPI。重复布局通知合并为一个回调 | 销毁旧 HWND 后其已排队输入失效；静态信息捕获失败可由后续现有更新按至少 1 秒间隔重试 |

这些是各级输入和任务的边界。视频字节预算不包含已出队的单个访问单元、既有下游 queue、解码器内部参考帧或 GPU 分配；时间阈值也不替代字节和缓冲数量限制。第三方或驱动阻塞仍需真机和长期运行验收。

## 已采纳的安全修正

- **关闭旧 HLS 桥接入口。** 原 ClearCast 补丁允许 `mlhls://.../master.m3u8`，`/action` 又能进入 UxPlay 旧播放列表改写函数。其分配长度与拷贝长度不一致，值得作为严重内存安全问题处理。当前 ClearCast 直接视频使用 GStreamer HTTP(S)/HLS，不需要该 FCUP/本地播放列表桥接；受控补丁拒绝旧 scheme、`/action` 和本地播放列表路由，保留正常 HTTP(S) 播放。拒绝在旧列表分配和所有权变更之前进行，缓存的安全 HTTP(S) 视频仍支持既有恢复语义。
- **发现请求不产生媒体副作用。** `/info`、`/server-info`、配对发现和 OPTIONS 在任何协议/CSeq/会话头组合下均不应占用媒体槽或停止已有传输。媒体鉴权在连接分类之前执行，不能因为缺少 CSeq 而进入未验证的 AirPlay 分类分支。
- **修复 EVENT 与请求体边界。** EVENT 不再对短头做无符号减法，也不对长度限定的数据使用无界字符串查找；拒绝长度溢出、重复/非数字 Content-Length 和畸形消息，正确处理前导字节及连续消息。`/fp-setup2` 检查最短请求体，UUID 查找不再依赖 Release 中失效的 assert。
- **加强 PIN 在线失败预算。** PIN 仍随机生成并在 60 秒后过期。同一接收器每 5 次有效挑战失败的冷却依次为 60、120、240、480、960、1800 秒；更换挑战不重置惩罚。成功 PIN 配对或一小时无有效挑战失败后恢复。未匹配来源及没有有效挑战的请求不计入失败，已保存设备的签名验证不依赖新 PIN 冷却。共享冷却也会延迟其他新设备配对，是防在线猜测的明确取舍，不能宣称消除了四位码的所有风险。
- **保护控制与停止。** 音频控制原先在检查所有者后通过旧入口重新捕获当前会话，存在检查与使用之间的竞态；现在一次捕获预期身份并在写入前复核。socket 超时使用同一次时钟读数，避免跨截止时间的无符号下溢，并检查非阻塞模式设置是否成功。
- **按验证连接和会话授权。** 音频 SETUP 只接受当前已验证连接 ID 及其原始来源，不能继承同 IP 兄弟连接或已关闭连接的权限。视频在成功 pair-verify 的 TCP 上把实际验签的 Ed25519 公钥、`X-Apple-Session-ID`、来源地址与 IPv6 scope 绑定；同一验证连接也可在后续 `/play` 首次提供会话头，兼容不在 pair-verify 中发送该头的客户端。分离 HTTP 连接只可续接已经在验证通道建立的会话，不能凭来源 IP 自行创建会话。活动所有者同时匹配会话和验证公钥，另一个已配对设备即使共享来源 IP 也不能夺取相同会话。最多保留 16 个有界授权，会话短暂断线允许最多 60 秒的同令牌续接，拒绝请求不延长窗口；正在播放或有活跃绑定连接时保留会话，媒体结束且无绑定连接时立即撤销。遗留 AirPlay 的该会话头是明文 bearer 关联值，不提供逐请求密码学完整性，不能据此声称防御能够截获会话头的中间人。
- **检查 HTTP 实际连接目标。** 初始视频和 HLS 嵌套来源共用 HTTP(S) 策略，拒绝 IPv4/IPv6 回环、IPv4-mapped 回环、未指定及组播目标，保留正常公网和内网单播。受控 `libgstsoup` 补丁把检查后的地址枚举器交给实际连接，不采用先解析检查、再让底层重新解析的做法；Host、TLS 主机名和 SNI 仍使用原始域名。自动重定向继续关闭，TLS 验证保持严格；媒体连接使用直接的受检目标，不经过系统 HTTP 代理。
- **监听跟随接收网卡。** 启动选择的网卡同时约束 IPv4、IPv6 TCP 和单播媒体端口，以及 mDNS 组播接口与接收路径；网卡不存在或无法满足绑定时失败，不退回全部网卡监听。已有 Windows TCP 独占设置保留。mDNS 的合法 legacy unicast 应答仍受选定接口约束。
- **限制本地数据消费。** 配对加载最多 16 MiB、4096 个不同设备，超限或读取中截短不返回部分信任列表；原生启动在更新身份之前失败，保留原文件和密钥。注册追加也受容量限制。删除配对使用固定缓冲保留无关字节；设置最多读取 4097 字节并拒绝超过 4096 字节的内容，诊断复制最多 16 KiB。读取失败时可使用既有“清除全部配对”入口，仍要求用户确认。
- **Windows 端口和编译加固。** TCP 监听使用 SO_EXCLUSIVEADDRUSE，UDP 沿用现有接收生命周期。GCC 构建对 `clearcast_receiver`、`airplay`、`renderers`、`llhttp`、`dnssd` 和 `playfair` 六个目标统一启用强栈保护及 MinGW fortify level 3，覆盖 mDNS 与 FairPlay 计算代码；接收 DLL 显式保留 ASLR、NX 和高熵地址空间标志。这些是纵深防御，不能保证检测所有越界或阻止所有代码执行，也不能代替边界检查。没有把 GCC 的其他控制流选项冒充 Windows CFG。

补丁顺序由 [Build-Receiver.ps1](../../scripts/native/Build-Receiver.ps1) 固定；不得只修改生成的上游源码。常规 HTTP `/server-info` 继续使用兼容的 `0x27F`，不因加固而扩大能力掩码。

旧播放列表改写函数没有在本轮逐项重写。当前交付通过关闭其所有网络入口消除可达路径；今后如恢复该桥接，必须先修复旧函数的分配、拷贝和错误退出行为，并重新验证可达性，不能直接撤掉拒绝逻辑。

## 外部审查中需要区分的意见

| 意见 | 判断及处理边界 |
| --- | --- |
| 两处 HLS 堆溢出、EVENT 越界及空指针 | 优先采纳。路径核查和生产处理器回归支持关闭不需要的旧桥接并修复仍使用的解析器；不把“可能远程执行”写成已证明的完整利用链 |
| 未配对 `/info` 影响投屏 | 采纳。在鉴权前分类和停止传输的顺序有实际代码依据 |
| 固定 PIN 一天可猜中 | 风险值得采纳，但“同一 PIN 长期不变”不符合现有随机和过期实现；概率还依赖持续获得有效挑战、速率和限流状态。采用有上限的递增冷却，不改变已有密码协议 |
| mDNS 对非 5353 源端口单播应答就是漏洞 | 不能这样判断。RFC 6762 §6.7 要求此类 legacy unicast 应答；反射风险应另外检查来源范围、速率及网络暴露，不能简单禁止合法协议行为。[协议依据](https://www.rfc-editor.org/rfc/rfc6762.html#section-6.7) |
| 一律禁止内网/回环 URL | 部分采纳：内网是正常投放来源；拒绝回环并在实际 socket 地址枚举处核对 DNS 结果，覆盖嵌套 HLS，保留严格 TLS、禁用凭据和自动重定向 |
| 只绑定广播网卡、取消按来源 IP 的兼容授权 | 采纳为统一接收网卡边界，并以已验证公钥与既有 AppleSession 关联跨连接控制；保留验证与播放使用同一 TCP、或验证通道已发行会话后另建 HTTP 的正常流程。具体发送端兼容性仍须真机确认 |
| 加 CFG | 值得作为工具链层面的后续加固；当前 GCC/MinGW 构建不能靠添加 MSVC `/guard:cf` 声称实现。栈保护和 fortify 是纵深防御，不能代替修复越界 |

SO_EXCLUSIVEADDRUSE 的安全作用及连接关闭后的复用限制见 [Microsoft Winsock 文档](https://learn.microsoft.com/en-us/windows/win32/winsock/using-so-reuseaddr-and-so-exclusiveaddruse)。必须同时回归端口独占、实际连接和快速重启，不能仅验证 setsockopt 返回成功。

## 验证入口

- 托管：`tests/managed/ManagedStateTests.csproj`；包括慢命令与连续生产、文件读取边界、损坏长行的字节保持与分配检查。
- 无接收端口原生：CMake/CTest 的 appsrc、总线、事件、音频状态、实际 EVENT 解析、HTTP 处理器、PIN 策略、session 授权纯策略，以及使用真实 SRP/签名验证的 HTTP 会话续接与所有者控制夹具；端口独占夹具仅使用临时端口。
- UI：`CLEARCAST_UI_BACKPRESSURE_ONLY=1`、`CLEARCAST_UI_DIAGNOSTICS_ONLY=1`，以及正常 UI harness。使用独立状态、阻塞消费者和大量更新，检查最终最新请求、并发上限、清空、关闭、捕获恢复和配对错误恢复。
- 真实 DLL 与应用：接收安全、配对重连、反复启停、HTTP MP4/HLS、桌面控制和窗口/全屏测试必须串行；遵循 [原生测试](testing-native.md) 和 [UI 测试](testing.md)。

媒体会话的直连 resolver 不修改全局代理或系统配置，但不会使用系统/环境 HTTP(S)/SOCKS 代理；仅能经过此类代理访问的媒体源可能不可达。TUN 的 IP 路由仍由 Windows 网络栈处理，具体 DNS/fake-IP 可达性依赖代理软件配置。DNS 使用既有 GLib 可取消解析与默认超时，HTTP I/O 沿用 15 秒超时；不把 socket I/O 超时等同于 DNS 超时。

网络地址/可用性通知最多保留一个已投递回调、一个活动探测和一个待检查标志。探测原绑定的接口 LUID、索引和地址，新增更优先的网卡不会打断仍然有效的播放；连续两次失效、间隔 250 毫秒后才停止并重新选择，旧探测结果不能停止新接收器。探测异常保留当前接收器，后续通知重试；无可用网卡时不积累自动重试任务。

自动夹具不是完整渗透测试，不替代真实 iPhone/iPad/Mac、实际账号内容、物理声卡/GPU 或长期弱网运行。新的安全拒绝路径和退避尤其需要关注真实发送端兼容性。
